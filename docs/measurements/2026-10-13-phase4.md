# Phase 4 측정 기록 (2026-10-13)

이 세션의 클라우드 컨테이너에서 실제로 돌린 결과다. 원자료는 `docs/measurements/raw/`.

## 측정 환경 (사실)

- 리눅스 컨테이너, CPU 4개, 메모리 16 GB, 디스크 하나. GPU 없음.
- 허브: `next start` 프로덕션 빌드, `FTL_ROLE=hub PHOTO_STORE=local`. 측정 하네스는
  `playwright.measure.config.ts`, `measure/`.
- 브라우저: Playwright Chromium, 헤드리스, 소프트웨어 렌더링.
- 백업 대상은 같은 디스크의 폴더다(USB 메모리가 아니다).

**현장 기기와 다르다(가정).** 빌린 노트북의 CPU·디스크·GPU, 실제 USB 메모리 속도, 현장 와이파이는
측정하지 않았다. 아래 숫자는 "이 코드가 이 정도 규모에서 무너지지 않는다"의 근거이고, 현장 속도의
약속이 아니다.

- 사실: 모든 상황에서 사진마다 노출 횟수 차이가 1 이하(F4), 굶는 사진 0장(F3).
- 바쁜 저녁 6시간(새 승인 362장, 지금 띄우기 40번, 숨김 55번): 지금 띄우기 최대 6초(F1), 새 사진 첫

- 가정: 시뮬레이션은 이미지가 즉시 준비된다고 본다. 실제 첫 노출은 이미지 받는 시간(아래 3번, 66 ms
  안팎)만큼 늦다.

## 3. 사진 3000장 부하 (`measure/seed.ts`, `measure/hub.measure.ts` 1번)

시드: 사진 3000장(장당 약 1.1 MB, 합계 3.4 GB). 예 60%(승인 1260, 반려 90, 숨김 90, 대기 360),
아니요 750, 무응답 450. 감사 기록 3336건. `db.json` 2.7 MB.

| 작업 (3000장 상태)                           | 중앙값   | 95%      | 최대   |
| -------------------------------------------- | -------- | -------- | ------ |
| 관리자 개요 API                              | 9 ms     | 30 ms    | 30 ms  |
| 검수 대기 목록 API (60장)                    | 7 ms     | 14 ms    | 14 ms  |
| 관리자 페이지 5종 (개요·검수·세션·사진·기록) | 17~34 ms | 23~44 ms | 44 ms  |
| 벽 피드 (`slots=8`, 32장 응답)               | 8 ms     | 13 ms    | 13 ms  |
| 벽 이미지 첫 요청 (1400 px 사본 생성)        | 66 ms    | 87 ms    | 87 ms  |
| 벽 이미지 두 번째부터                        | 10 ms    | 12 ms    | 12 ms  |
| 부스 업로드 + 동의 (실제 크기 JPEG)          | 284 ms   | 342 ms   | 342 ms |
| 스태프 승인                                  | 35 ms    | 46 ms    | 46 ms  |
| 동시 14건 (승인 5, 업로드 3, 피드 3, 개요 3) | 271 ms   | 737 ms   | 737 ms |
| USB 백업 첫 번째 (3.4 GB 복사)               | 22.7 초  |          |        |
| USB 백업 그다음 (바뀐 것만)                  | 0.5 초   |          |        |

- 허브 메모리(RSS): 220 MB에서 시작, 끝에 256 MB.
- 사실: 허브는 쓸 때마다 `db.json` 전체를 다시 쓴다. 쓰기 한 번 시간이 사진 수에 비례해 늘었다
  (250장 2 ms → 3000장 13 ms, 중앙값). `raw/seed.json`.
- 추정: 1만 장이면 쓰기 한 번 45 ms 안팎. 하룻밤 수백~수천 장 규모에서는 문제없다. 그보다 훨씬 많아지면
  `db.json` 방식(D47)을 다시 봐야 한다.
- 가정: 실제 USB 2.0 메모리(20~30 MB/s)라면 첫 백업이 2~3분. 그동안 허브는 계속 동작한다(백업은
  복사만 하고 쓰기를 막지 않는다).

### 이 측정에서 찾아 고친 것

- `HUB_BACKUP_MINUTES` 를 아주 크게(약 35791분 넘게) 적으면 Node 타이머가 넘쳐 1 ms마다 백업을 다시
  시도했다. 이제 1440분(하루)까지만 받는다(`lib/server/env.ts`, 단위 테스트 추가).

## 4. 네트워크 차단

| 끊긴 곳                 | 시험                                                                                                                   | 결과 |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---- |
| 부스 ↔ 허브             | `e2e/offline.spec.ts`: 사진은 기기에 보관, 가짜 QR 없음, 복구 후 한 번만 전송, 새로고침해도 유지, 동의 답도 함께 감    | 통과 |
| 허브 ↔ 클라우드(인터넷) | `e2e/cloud.spec.ts`: "QR 준비 중", 인터넷이 돌아오면 QR이 저절로 나옴, 동의는 허브에 남음, 허브 삭제가 클라우드까지 감 | 통과 |
| 허브만 (인터넷 없음)    | `e2e/hub.spec.ts`: 촬영 → 동의 → 승인 → 벽 → 숨김을 클라우드 없이                                                      | 통과 |
| 미디어월 ↔ 허브         | `e2e/wall-scene.spec.ts` (이번에 추가): 스태프 표시, 잠깐은 그대로, 120초 뒤엔 사진 0장, 연결되면 저절로 복귀          | 통과 |

- 사실: 미디어월이 끊기면 이미 받아 둔 사진으로 계속 돌다가, 사진이 적으면 120초 전에도 빈 줄이 될 수
  있다(시험에서 11장일 때 73초). 숨김·삭제를 모르는 채 보여 주지 않으려는 의도된 동작이다.
- 막힘: 현장 와이파이·공유기에서의 실제 차단 시험. 리허설 때 공유기 전원을 뽑아 본다.
