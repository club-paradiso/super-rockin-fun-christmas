# 카메라 자동 보정 (Intelligent Camera Engine)

결정: `docs/DECISIONS.md` D120. 상태 표기는 **구현됨 / 검증됨 / 미검증 / 막힘** 네 가지만 쓴다.
봉사자용 한 장 안내: `docs/CAMERA_ENGINE_GUIDE_KO.md`.

**이 문서가 증명하지 않는 것.** 실제 iPad mini 4에서 돌려 본 적이 없다. 아래 "검증됨"은 전부
Node(Vitest)와 헤드리스 Chromium(Playwright)에서 나왔다. 센서 부호, 카메라 화각, 처리 시간,
Safari 15의 WebGL·CSS 동작은 모두 **미검증**이다. 그래서 기본값은 **꺼짐**이고, 19절 점검표를
사람이 마치기 전에는 "운영 가능(production ready)"이라고 부르지 않는다.

## 1. 한눈에

키오스크가 옆으로 기울었거나(롤) 뒤로 젖혀졌을 때(피치), 태블릿의 기울기 센서로 그 각도를 읽어
사진을 바로잡는다. 직원이 각도를 재거나 입력할 필요가 없다.

| 이름              | 하는 일                                                               |
| ----------------- | --------------------------------------------------------------------- |
| Smart Level       | 좌우 기울기(롤)를 되돌린다                                            |
| Smart Perspective | 앞뒤 기울기(피치) 때문에 세로선이 모이는 것을 줄인다                  |
| Portrait Guard    | 사람이 늘어나 보일 만큼은 보정하지 않는다                             |
| Smart Crop        | 빈 모서리가 생기지 않는 가장 작은 확대만 한다                         |
| Sensor Stabilizer | 센서 값을 하나의 흔들리지 않는 기울기로 만든다                        |
| 통합 렌더링       | 롤·피치·확대·자르기를 한 번의 변환으로 그린다. 미리보기와 사진이 같다 |
| Safe Capture      | 무엇이 실패하든 사진은 예전 방식 그대로 찍힌다                        |

목표는 기하학적으로 완벽한 수직·수평이 아니다. 사람이 자연스럽게 보이는 것이 먼저다. 그래서 피치는
일부만 보정한다(7·8절).

## 3. 좌표와 부호

세 좌표계, 모두 오른손 좌표계다.

| 좌표계 | x                         | y               | z                           |
| ------ | ------------------------- | --------------- | --------------------------- |
| 기기   | 화면 오른쪽(원래 방향)    | 화면 위쪽       | 화면에서 보는 사람 쪽 (W3C) |
| 화면   | 지금 보이는 페이지 오른쪽 | 페이지 위쪽     | 화면에서 보는 사람 쪽       |
| 카메라 | 사진 오른쪽(반전 전)      | 사진 **아래쪽** | 광축, 찍히는 쪽으로         |

- 기기 → 화면: 페이지 회전각(`screen.orientation.angle`, Safari 16.4 미만은 `window.orientation`)만큼
  돌린다. 90이면 기기를 반시계로 돌린 것이고 `x' = −y, y' = x`.
- 화면 → 카메라: 전면 카메라는 화면 밖을 보므로 `(−x, −y, z)`, 후면 카메라는 `(x, −y, −z)`.
- **롤 +**: 사진 속 장면이 시계 방향으로 돌아 보이는 것. 전면 카메라에서는 **화면을 마주 보고
  태블릿이 시계 방향으로 기운 것**과 같다.
- **피치 +**: 카메라가 위를 보는 것. 전면 카메라에서는 **태블릿이 뒤로 젖혀진 것**.
- 직원이 입력하는 보정값도 같은 부호다.

"위" 벡터 `u`(카메라 좌표)에서 `롤 = atan2(u.x, −u.y)`, `피치 = atan2(u.z, hypot(u.x, u.y))`.
각도는 맨 끝에서만 읽는다. 중간에는 벡터만 다루므로 ±180° 경계나, 태블릿을 세웠을 때 beta·gamma가
튀는 구간(짐벌 락)에서 평균이 깨지지 않는다.

**`gamma`를 롤로 쓰지 않는다.** 세워 둔 태블릿을 5° 기울이면 W3C 각도는 `beta 85, gamma 90`이다.
`gamma`는 롤과 무관하게 ±90 근처에 있다. 엔진은 `R = Rz(alpha)·Rx(beta)·Ry(gamma)`의 셋째 행
`(−cos β·sin γ, sin β, cos β·cos γ)`를 "위"로 쓴다. `alpha`(나침반)는 여기서 사라진다.

부호가 실제 iPad mini 4에서 맞는지는 **미검증**이다. 19절 1~3번이 그 확인이다.

## 4. 센서 읽기와 안정화

- **두 이벤트.** `deviceorientation`(시스템이 이미 융합한 값, 조용함, 부호가 브라우저마다 같음)을
  먼저 쓴다. `devicemotion`의 `accelerationIncludingGravity`는 예비이자 교차 확인이다. iOS는 이
  값의 부호가 W3C 문서와 반대라서(눕힌 태블릿이 z = −9.81), 방향 이벤트가 있으면 그것과 같은
  쪽으로, 없으면 "페이지 위쪽이 아래보다 위를 향한다"는 규칙으로 부호를 정한다.
- **버리는 값.** 숫자가 아닌 값, NaN·Infinity, 길이가 중력(9.81)에서 20% 넘게 벗어난 가속도(누가
  만지거나 들고 있는 중), 지금 값에서 8° 넘게 튄 값 하나.
- **필터.** 단위 벡터에 시간 상수 0.35초의 저역 필터. 초당 60개 중 약 12개만 처리한다.
- **정착.** 6개 이상, 0.6초 이상, 흔들림 0.6° 미만이면 게시한다. 단위 테스트에서 0.5~1.5초.
- **이력.** 게시된 값은 지금 값이 0.4° 넘게 벗어나야 바뀐다. 가만히 선 부스는 한 번 게시하고
  그 뒤로는 계획도, 그리기 상태도 다시 만들지 않는다.
- **옮긴 경우.** 튄 값이 12개 연속이면 태블릿이 다른 자세로 놓인 것으로 보고 처음부터 다시 잰다.
- **멈춘 경우.** 3초 동안 값이 없으면 "멈춤". 다시 들어오면 처음부터 다시 잰다(그 사이 태블릿이
  어떻게 됐는지 모르므로 옛 값을 쓰지 않는다).
- **화면을 누를 때.** 게시된 값은 가만히 있을 때 확인된 값이라, 손님이 셔터를 누르는 순간의 흔들림
  때문에 사라지지 않는다. 마지막 확인 후 3초까지 쓸 수 있다.
- **두 센서가 다를 때.** 5° 넘게 다르면 신뢰도를 낮춘다(보정이 줄어든다).

자동으로 잰 기울기는 **저장하지 않는다.** 페이지를 다시 열면 다시 잰다(1초 남짓). 그래서 "어제
자리의 값이 오늘 자리에 쓰이는" 일이 없다.

## 5. 카메라 값과 프로파일

브라우저는 카메라의 초점거리나 화각을 알려 주지 않는다. 엔진에 필요한 것은 **스트림 긴 변 방향의
화각** 하나다. 초점거리(px)는 `긴 변 ÷ 2 ÷ tan(화각 ÷ 2)`, 주점은 스트림 한가운데, 픽셀은
정사각형으로 본다.

- 프로파일은 `config/camera-engine.ts`의 `CAMERA_PROFILES`에 있다. 지금은 `generic-front` 하나,
  **55° 추정값**이다. iPad mini 4 전면 카메라 화각은 잰 적이 없어서 실측값처럼 적지 않았다.
- 추정값은 일부러 좁게 잡았다. 화각을 실제보다 좁게 가정하면 원근 보정이 모자라고, 넓게 가정하면
  지나치다. 모자란 쪽이 안전하다.
- 추정 프로파일은 피치 요청의 75%만 받는다(`assumedProfileShare`).
- 롤 보정은 화각과 무관하다(주점을 중심으로 한 회전).
- 직원이 관리자 화면 「고급 → 카메라 화각」에 잰 값을 넣으면 그 값을 쓰고 100%를 받는다.

### 화각 재는 법

1. 태블릿을 벽에서 정확히 재서 `d` cm 떨어진 곳에 벽과 나란히 세운다.
2. `/camera-lab`의 미리보기에 벽의 자(또는 테이프 두 줄)를 비춘다. **스트림 긴 변 방향**으로
   화면 양 끝에 걸리는 눈금 사이 거리 `w` cm를 읽는다. 미리보기는 4:3으로 잘린 화면이므로, 가로로
   세운 태블릿(16:9 스트림)에서는 잘린 가로 대신 **세로 전체**를 재고 아래 식에 16/9를 곱한다.
3. `화각 = 2 × atan(w ÷ 2 ÷ d)`.
4. 값을 `CAMERA_PROFILES`에 `source: "measured"`로 추가하거나, 관리자 화면에 입력한다.

## 6. Smart Level (롤)

- 0.3° 아래는 손대지 않고 1.0°부터 전부 되돌린다. 사이는 매끄럽게 이어진다. 남는 기울기는
  어디서도 0.5°를 넘지 않는다(단위 테스트).
- 최대 15°까지 되돌린다. 15~30°는 15°만, 30°를 넘으면 설치 오차가 아니라고 보고 아무것도 안 한다.
- 회전 후 빈 모서리가 없도록 Smart Crop이 확대한다. 확대가 1.30배를 넘어야 하면 롤을 그만큼
  덜 되돌린다. 가로 스트림(1280×720)에서 15°는 14.4°까지만 된다.
- 카메라가 45° 넘게 위·아래를 보면 중력으로 롤을 읽기 어려워서 줄이고, 60°부터는 0이다.

| 롤  | 가로 스트림(1280×720) 확대 | 세로 스트림(720×1280) 확대 |
| --- | -------------------------- | -------------------------- |
| 3°  | 1.07                       | 1.04                       |
| 5°  | 1.11                       | 1.06                       |
| 10° | 1.22                       | 1.12                       |
| 15° | 1.30 (14.4°까지)           | 1.16                       |

세로로 세운 태블릿은 스트림이 세로로 길어서 4:3 사진 위아래에 여유가 있다. 그래서 같은 롤에 확대가
덜 든다. (iPad가 세로일 때 스트림이 720×1280으로 오는지는 **미검증**이다.)

## 7. Smart Perspective (피치)

카메라가 제자리에서 돌기만 했다면, 돌기 전과 후의 사진은 호모그래피 하나로 이어진다.

```
H = K_target · R_correction · K_source⁻¹
R_correction = Rz(롤 − Δ롤) · S · Rx(Δ피치) · Rz(−롤)
```

오른쪽부터 읽는다. 롤을 먼저 풀어 x축을 수평으로 만들고, 그 수평축을 중심으로 피치를 되돌리고,
보정하지 않을 롤을 다시 얹는다. 순서가 바뀌면 수평선이 기운다(단위 테스트).

- **K_target.** 초점거리에 확대를 곱하고, 주점을 옮겨 **사진 한가운데가 제자리에 있게** 한다. 이게
  없으면 피치 9°를 되돌릴 때 사람이 사진 아래로 100px 넘게 밀린다(1280×720 기준, 단위 테스트).
- **S = diag(1, cos Δ피치, 1).** Portrait Guard의 몫이다(8절).
- 샘플링은 역방향이다. 출력 픽셀마다 `H⁻¹`로 원본 위치를 구하고 동차 좌표를 나눈다. 나눗셈은
  픽셀마다 한다(꼭짓점에서만 하면 직선이 휜다).

**요청 곡선.** `7.5° × tanh(피치 ÷ 7.5°)`. 작은 피치는 거의 전부, 큰 피치는 줄어드는 몫, 최대 7.5°.
1.2° 아래는 0, 3.2°부터 곡선 그대로. 계단이 없다(0.02° 간격으로 훑는 단위 테스트).

| 피치 | 실측 프로파일 요청 | 추정 프로파일(지금) 실제 적용 |
| ---- | ------------------ | ----------------------------- |
| 2°   | 0.7° (35%)         | 0.5° (26%)                    |
| 5°   | 4.4° (87%)         | 3.3° (66%)                    |
| 10°  | 6.5° (65%)         | 4.9° (49%)                    |
| 15°  | 7.2° (48%)         | 5.4° (36%)                    |
| 25°  | 7.5° (30%)         | 5.6° (22%)                    |

25°를 넘으면 직원에게 경고를 띄우고, 35°부터 줄여 50°에서 0이 된다.

### 할 수 없는 것

회전 재투영은 카메라의 **위치와 높이를 바꾸지 못한다.** 아래에서 올려다본 얼굴(턱이 크고 이마가
작은 얼굴)은 그대로다. 찍히지 않은 영역을 만들어 내지도 않는다. 바뀌는 것은 사진면의 기울기,
곧 세로선이 모이는 정도뿐이다. 키오스크를 눈높이에 두는 것을 대신하지 못한다.

## 8. Portrait Guard

피치만큼 순수하게 회전하면 사진 한가운데가 세로로 `1/cos²`, 가로로 `1/cos` 늘어난다. 평평한
벽에는 맞는 보정이지만, 가운데 있는 얼굴은 세로로 길어진다(10°에서 1.5%, 20°에서 6.4%).

1. **가운데는 비율 유지.** `S`가 그 차이를 되돌린다. 가운데의 국소 변형은 등방(늘어남 1.000)이
   되고, 세로선이 모이는 것만 풀린다. `S`는 수평 기준 좌표에서의 축 방향 배율이라 세로선은
   그대로 세로다.
2. **늘어남 한계.** 출력 9×9 지점에서 변환의 야코비안을 구하고 두 특이값의 비(늘어남)를 본다.
   가운데 영역(가로 20~80%, 세로 10~90%)은 **1.05**, 사진 전체(단체 사진의 가장자리 사람)는
   **1.10**, 국소 확대는 **1.35**를 넘지 않는다.
3. **가장 큰 강도 찾기.** 요청 각도의 0~100% 중 한계를 모두 지키는 가장 큰 값을 고른다(8단계로
   훑고 12번 이분). 한계에 걸리면 딱 그 한계에 멈춘다. 각도를 키워도 적용값이 튀지 않는다.
4. 롤은 닮음 변환이라 아무도 늘이지 않는다. Portrait Guard는 롤을 줄이지 않는다.

지금의 55° 추정 프로파일에서는 요청 자체가 작아서 Guard가 걸리지 않는다(가운데 늘어남 최대 약
1.03). 화각이 넓은 카메라(95°)에서는 걸리고, 상태에 "사람이 늘어나 보이지 않게 앞뒤 보정을
줄였어요"가 뜬다.

Guard를 끄면(`portraitGuard: false`) `S`가 빠지고 늘어남 한계도 빠진다. 확대와 잘림 한계는 남는다.

얼굴 인식, 얼굴 기준 메시 변형은 **구현하지 않았다.** 기하만으로 한계 안에 들어왔고, iPad mini 4의
성능·메모리를 재기 전에는 넣지 않는다. 얼굴이나 체형을 고치는 기능은 이 엔진에 없다.

## 9. Smart Crop

- 출력 사각형의 네 꼭짓점이 모두 스트림 안에 들어오는 **가장 작은 확대**를 이분법으로 찾는다.
  호모그래피는 사각형을 볼록 사각형으로 옮기므로(지평선이 그 안에 없을 때. `w`로 확인한다)
  꼭짓점이 안이면 전부 안이다.
- 기준점은 사진 한가운데, 고정이다. 확대는 1 미만이 되지 않는다(원래 구도보다 넓어지지 않는다).
- 크롭 밖의 스트림도 쓴다. 16:9 스트림에서 4:3을 자르고 남는 좌우(세로 스트림이면 위아래)가
  회전할 때 안으로 들어온다.
- 롤과 피치를 따로 자르지 않는다. 변환 하나, 확대 한 번, 재샘플링 한 번이다. (WebGL 경로는
  프레임을 2D 캔버스에 1:1로 옮긴 뒤 올린다. 이 복사는 재샘플링이 아니다.)
- 피치 몫의 확대는 1.15배, 또는 롤이 이미 쓴 확대 + 0.04까지. 전체는 1.30배까지.
- 사진 크기와 비율은 보정 전과 같다(960×720 등). 틀 합성은 달라지지 않는다.
- "잘림(추정)"은 보정 전 사진 중 프레임 밖으로 나가는 몫이다(24×24 지점).

## 10. 그리기와 Safari 15

| 순서 | 무엇으로                 | 무엇을                    |
| ---- | ------------------------ | ------------------------- |
| 1    | WebGL 1 (GLSL ES 1.00)   | 롤 + 피치, 재샘플링 한 번 |
| 2    | 2D 캔버스 `setTransform` | **롤만** (아핀 변환뿐)    |
| 3    | 예전 `grabFrame`         | 보정 없음                 |

- WebGL 2, 확장, float 텍스처, `requestVideoFrameCallback`, `OffscreenCanvas`를 쓰지 않는다.
- 텍스처는 2의 거듭제곱이 아니어도 되게 `CLAMP_TO_EDGE` + `LINEAR`, 밉맵 없음.
- 프래그먼트 셰이더는 `highp`가 있으면 쓰고, 행렬은 0~1 좌표로 넘겨 숫자를 작게 유지한다.
- **카메라 `<video>`를 WebGL에 직접 올리지 않는다.** 프레임을 먼저 2D 캔버스에 그리고(부스가
  원래 카메라를 읽던 방식) 그 캔버스를 텍스처로 올린다. iOS에서 카메라 영상 텍스처가 검게 나오던
  사례가 있어서 가장 확실한 경로를 골랐다.
- **검은 화면 검사.** 원본은 밝은데 결과가 검으면(오류 없이 WebGL이 실패하는 경우) 버린다.
  8×8 픽셀로 줄여 읽으므로 큰 픽셀 읽기는 없다.
- **컨텍스트 손실.** 실패하면 새 컨텍스트로 한 번 더, 또 실패하면 그 손님의 남은 사진은 2D
  캔버스(롤만)로, 미리보기도 따라 바뀐다. 다음 손님 때 WebGL을 다시 시도한다.
- 엔진 전체가 WebGL 컨텍스트 하나, 프로그램 하나, 텍스처 하나를 쓰고 사진마다 새로 만드는 것은
  결과 캔버스 한 장뿐이다.
- 2D 캔버스로는 원근(피치)을 그리지 않는다. 메시 근사는 넣지 않았다. 불안정한 피치 보정보다
  롤만 맞은 사진이 낫다.
- 기준 계산(`warp-cpu.ts`)은 손님 사진에 쓰지 않는다. iPad mini 4에서의 속도를 잰 적이 없다.

## 11. 미리보기 = 사진

미리보기 `<video>`에 계획의 호모그래피를 **CSS `matrix3d`**로 준다. 브라우저 합성기가 GPU에서
적용하고, 카메라가 도는 동안 스크립트는 아무것도 그리지 않는다. A8 칩에서 프레임마다 비디오를
텍스처로 올리는 것보다 훨씬 가볍다.

- `matrix3d`는 4×4 사영 행렬이라 계획의 호모그래피 **그 자체**다. `perspective()`나 `rotateX()`
  근사가 아니다. 사진은 이 요소에서 찍지 않는다.
- 엔진이 켜지면 `<video>`를 "cover" 크기의 **전체 프레임**으로 놓는다(크롭 밖 부분이 회전해
  들어올 수 있게). 상자가 넘치는 부분을 잘라 낸다.
- 좌우 반전은 같은 행렬에 들어 있다. 반전 정책은 바뀌지 않았다.
- 흑백 틀의 CSS 필터와 함께 쓸 수 있다.
- 보정할 것이 없거나 엔진이 꺼져 있으면 요소는 예전 그대로다(`object-fit: cover` + `scaleX(-1)`).

같은 지점이 미리보기와 사진에서 같은 원본 픽셀을 가리키는지 단위 테스트가 행렬로 확인하고, E2E가
실제 화면을 찍어 사진과 비교한다. Safari 15에서 `<video>`의 `matrix3d`가 똑같이 그려지는지는
**미검증**이다.

## 12. 세션 고정

- 손님의 **첫 카운트다운**에 기울기를 고정한다. 그 세션의 여섯 장과 「다시 찍기」가 모두 같은
  보정을 받는다. 그동안 센서가 뭐라고 하든(누가 부스에 기대든, 센서가 멈추든) 바뀌지 않는다.
- 고정 시점에 정착된 기울기가 없으면 그 손님은 보정 없이 찍힌다. 중간에 생기지 않는다.
- 촬영 중에 화면이 회전하면 고정값이 맞지 않으므로 그 손님은 보정을 뗀다.
- 손님이 떠나면(처음 화면) 고정을 풀고 다시 센서를 본다.
- 직원이 바꾼 설정도 처음 화면에서만 받아들인다. 촬영 중에는 바뀌지 않는다.

## 13. 대체 동작

| 단계 | 상태(`state`) | 언제                                          |
| ---- | ------------- | --------------------------------------------- |
| 1    | `full`        | 롤과 피치를 요청대로 보정                     |
| 2    | `reduced`     | Portrait Guard나 확대 한계 때문에 피치를 줄임 |
| 3    | `roll-only`   | WebGL이 없거나 실패                           |
| 4    | `manual`      | 직원이 「수동」으로 넣은 값                   |
| 5    | `original`    | 그 밖의 전부. 사진은 예전 방식 그대로         |
| —    | `level`       | 정상인데 바로 서 있어서 할 일이 없음          |

`original`이 되는 이유(`reason`): 센서 권한을 아직 안 물음 · 거부됨 · 센서 없음 · 재는 중 · 멈춤 ·
흔들림 · 신뢰도 낮음 · 너무 많이 기욺 · 어느 쪽 카메라인지 모름 · 아이폰 원격 카메라 · 촬영 중 화면
회전 · 계산 불가 · 그리기 실패.

엔진의 어떤 예외도 촬영으로 올라가지 않는다. `grabFrame`은 보정이 `null`을 주거나 던지면 예전
코드로 그 프레임을 찍는다. 카메라 권한이 없을 때의 화면은 예전 그대로다.

## 14. 관리자 설정

`/admin/settings` → 「카메라 자동 보정」. 저장은 감사 로그에 남는다(`ftl_settings_set_camera_engine`).

| 설정             | 값                       | 뜻                                                  |
| ---------------- | ------------------------ | --------------------------------------------------- |
| 방식             | 끄기(기본) / 자동 / 수동 | 끄기: 예전과 똑같음. 자동: 센서. 수동: 아래 값만    |
| 좌우 기울기 보정 | 켬 / 끔                  | Smart Level                                         |
| 앞뒤 기울기 보정 | 켬 / 끔                  | Smart Perspective                                   |
| 사람 왜곡 방지   | 켬 / 끔                  | Portrait Guard                                      |
| 좌우 보정값(°)   | −15 ~ 15                 | 자동: 센서 값에 더함. 수동: 이 값이 곧 기울기       |
| 앞뒤 보정값(°)   | −25 ~ 25                 | 위와 같음                                           |
| 카메라 종류      | 프로파일                 | `CAMERA_PROFILES`                                   |
| 카메라 화각(°)   | 비움 / 30 ~ 110          | 직접 잰 값                                          |
| 보정값 초기화    | 버튼                     | 보정값을 0으로, 각 부스가 기울기를 처음부터 다시 잼 |

- 부스별 실시간 상태는 `/admin/kiosks`의 「자동 보정」 줄과 「자세히」에 있다(부스 하트비트, 45초
  간격). 허브에서는 부스의 직원 도움말 메뉴(왼쪽 위 3초 누르기)에도 1초마다 갱신되어 나온다.
- 표시되는 각도는 **센서로 추정한 값**이다. 사진에서 잰 값이 아니고, 화면에도 그렇게 적혀 있다.
- 한 태블릿만 시험할 때는 주소에 `?engine=auto`(또는 `manual`, `off`)와 `?tilt=좌우,앞뒤`를 붙인다.
  주소가 직원 설정을 이긴다. `?looks=`, `?retouch=`와 같은 시험용 도구다.
- 설정 스키마는 `event_settings.camera_engine`(jsonb) 한 칸이다. 칸이 없거나 값이 비어 있으면
  기본값(끄기)으로 읽는다. 마이그레이션 `20261127090000_camera_engine.sql`.

## 15. 개인정보

- 센서 값과 보정 계산은 태블릿 안에서만 쓴다. 들어오는 값 그대로는 저장도, 기록도, 전송도 하지 않는다.
- 하트비트로 가는 것: 상태 코드, 0.1° 단위로 반올림한 추정 기울기와 적용값, 확대·잘림, 마지막 오류
  코드. 사진이나 얼굴에 관한 것은 없다. 서버는 계약에 맞지 않는 값은 통째로 버린다.
- 얼굴 인식·생체 정보·외부 API·새 추적 없음. 사진 게시·다운로드·인증·권한은 바뀌지 않았다.

| "좌우 기울기만 보정하고 있어요"      | WebGL 불가. 사진은 정상. 페이지를 새로고침하면 다시 시도한다.                                       |
| 사진이 너무 많이 잘린다              | 「확대·잘림」을 본다. 1.2배가 넘으면 거치대를 바로 세우는 것이 답이다.                              |
| 얼굴이 길어 보인다                   | 「사람 왜곡 방지」가 켜져 있는지 확인. 켜져 있어도 그러면 「앞뒤 기울기 보정」을 끈다.              |
| "너무 많이 기울어서 보정하지 않아요" | 롤 30° 초과 또는 거의 누운 상태. 거치대 문제다.                                                     |
| 아무 변화가 없다                     | 방식이 「끄기」인지, 주소에 `?engine=off`가 붙어 있는지, 새 손님부터 적용된다는 점을 확인.          |

## 19. 실기기 점검표 (iPad mini 4 · iPadOS 15 · Safari)

`/camera-lab`은 개발 서버, Vercel 미리보기 배포, `CAMERA_LAB=1`인 서버에서 열린다. OS 버전, 배포
SHA, 거치 방향을 함께 적는다. 전부 **미검증**이다.

## 20. 되돌리기

위에서부터, 가벼운 순서다.

1. **관리자 화면 → 카메라 자동 보정 → 끄기 → 저장.** 각 부스는 다음 손님부터 예전 그대로다. 배포가
   필요 없다.
2. 한 태블릿만: 주소에 `?engine=off`.
3. 코드를 되돌려야 하면 이 기능의 PR을 revert한다. 마이그레이션은 칸 두 개와 함수 하나를 **더하기만**
   했으므로 그대로 두어도 예전 코드가 돌아간다. 굳이 지우려면:
   `alter table public.event_settings drop column camera_engine; alter table public.kiosks drop column camera_engine; drop function public.ftl_settings_set_camera_engine(jsonb, uuid);`
4. 꺼져 있는 동안 부스는 센서를 듣지 않고, 권한을 묻지 않고, WebGL 컨텍스트를 만들지 않는다.
