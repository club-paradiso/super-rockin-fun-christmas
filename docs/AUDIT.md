# FOLLOW THE LIGHTS — Phase 0 감사 (2026-10-12)

새 요구사항(현장 우선, 한 달 운영, 빨랫줄 미디어월, 출력 포함 가능성)을 기준으로 기존 레포를 다시
조사한 결과다. 상태 표기는 **구현됨 / 검증됨 / 미검증 / 막힘** 네 가지만 쓴다. 문장마다 근거가
무엇인지 구분한다: **사실**(코드·실행 결과로 확인), **가정**(답을 받기 전 임시값), **추정**(근거는
있지만 측정하지 않음).

## 1. 한 줄 요약

레포는 비어 있지 않다. 키오스크·QR 다운로드·관리자 검수·미디어월까지 **클라우드 전제
(Vercel + Supabase)** 로 이미 구현돼 있고 자동 테스트도 통과한다. 그러나 이번 요구사항과
**근본적으로 부딪히는 결정 세 가지**(출력 금지, 클라우드 기준 저장소, 이메일 기반 스태프 로그인)가
있어서, 이 셋을 정하기 전에는 Phase 1 설계를 확정할 수 없다.

### 2.1 E2E 결과

`npm run test:e2e` (프로덕션 빌드, 키오스크 인증 켬, 목업 카메라 + Chromium 가짜 웹캠): **13 통과, 10

통과한 것: 정상 촬영 → 업로드 → QR → 휴대폰 페이지 → 동의 YES → `PENDING` / 동의 NO여도 다운로드
유지 / 한 컷만 재촬영 / 없는 링크 404 / 네트워크 끊김 시 큐 저장·가짜 QR 없음·복구 후 1회 업로드 /
큐 상태에서 새로고침해도 사진 유지 / 미등록 기기 차단 / 비밀값이 브라우저 JS에 없음 / 미등록 화면에
벽 안 뜸 / 등록된 벽이 실제 피드 반영 / 실제 `getUserMedia` 경로 / 카메라 권한 거부 화면.

**검증되지 않은 것:** 인터넷 없는 상태에서 검수 → 벽 노출(지금 구조로는 불가능, §4 C2), 벽 장시간
구동, 사진 수천 장 부하, 실제 해상도 렌더링.

## 4. 새 요구사항과 정면으로 충돌하는 기존 결정

이 셋은 내가 임의로 고르면 안 되는 문제다. 멈춤 조건에 해당한다.

### C1. 출력(프린트)

- **사실:** `CLAUDE.md`와 `docs/DECISIONS.md` D4는 "출력 없음"을 제품 원칙으로 못 박았다. 프린터,
  출력 큐, 인쇄 레이아웃 코드는 하나도 없다.
- **새 요구사항:** 흐름에 "출력", 상태판에 "프린터 상태", 합성은 "인쇄용 300dpi" 버전을 따로 만들라고 한다.
- **영향:** 출력을 넣으면 프린터 선택, 무인 인쇄 방식, 용지 소진 대응, 4x6 → 2x6 재단 레이아웃이
  전부 새로 생긴다. 넣지 않으면 지금 구조 그대로 간다.
- **참고 (사실):** 지금 프레임 `starlight-strip`은 1200×3600 = 2x6인치 600dpi다. 4x6 용지에 두 장을
  나란히 놓는 레이아웃(2400×3600 @600dpi 또는 1200×1800 @300dpi)은 프레임 데이터만 추가하면 된다.

### C2. 기준 저장소: 클라우드 vs 현장 허브

- **사실:** 지금은 모든 데이터가 Supabase(클라우드)에 있다. 키오스크는 인터넷이 끊기면 사진을 기기에
  쌓아 두지만, 그동안 다음이 멈춘다.
  - 새 사진이 서버에 도착하지 않으므로 검수도, 벽 노출도 없다.
  - 스태프 로그인과 검수 화면은 Supabase에 직접 의존한다.
  - 미디어월은 서버 응답 없이 2분이 지나면 화면의 모든 사진을 내린다(D38). 숨김·삭제를 알 수 없게
    되므로 일부러 그렇게 만들었다.
- **새 요구사항:** "인터넷이 끊겨도 촬영 → 출력 → 미디어월 표시가 계속 돌아가야 한다", 완료 기준 1번은
  "인터넷 없는 상태에서 촬영 → 동의 → 검수 → 벽 노출 E2E 통과"다. **지금 구조로는 불가능하다.**
- **영향:** 현장 LAN의 허브 PC를 기준 저장소로 바꾸면 데이터 계층, 인증, 배포, 운영 문서가 바뀐다.
  다행히 저장 계층은 이미 인터페이스로 분리돼 있고(`PhotoService` + 백엔드 3종), 파일 기반 로컬
  백엔드도 검수·설정·감사·벽 노출 규칙까지 Supabase와 같은 계약 테스트(`tests/helpers/ops-contract.ts`)를
  통과한다(사실, `tests/unit/photo-service.test.ts`). 로컬 모드에서 관리자 화면이 503을 내는 이유는
  저장소가 아니라 스태프 로그인이 Supabase Auth에만 묶여 있기 때문이다(`lib/staff-auth/server.ts`).
- **QR의 물리적 한계 (사실):** 손님 휴대폰은 보통 셀룰러로 접속하므로 QR 링크는 공개 인터넷 주소여야
  한다. 인터넷이 끊긴 동안 찍은 사진의 QR은 그 자리에서 만들 수 없다. 지금도 키오스크는 가짜 QR을
  보여주지 않는다. 현장 우선 구조에서도 이 점은 같다.

### C3. 스태프 로그인

- **사실:** 지금은 Supabase 이메일 6자리 코드 + 허용 목록이다. 인터넷과 메일 수신이 필요하다.
- **새 요구사항:** "비밀번호/PIN 보호".
- **영향:** 현장 허브로 가면 이메일 코드는 인터넷이 끊기면 못 쓴다. LAN 안에서 동작하는 PIN 방식이
  필요하다. 이건 `CLAUDE.md`의 "스태프 = Supabase Auth" 원칙을 바꾸는 일이다.

## 8. 질문 목록 (한 번에)

결정이 필요한 것부터 적었다. Q1~Q3은 설계 전체가 갈리는 질문이다.

**Q1. 출력을 하나요?** 한다면 프린터 기종(또는 후보), 용지(4x6을 2x6 두 장으로 자르는 방식인지),
한 번 촬영에 몇 장인지. 안 한다면 지금처럼 QR만 둔다.

**Q2. 인터넷이 끊겨도 검수와 벽 노출까지 계속 돼야 하나요?** 그렇다면 현장 LAN에 허브 PC 한 대를
두고 그걸 기준 저장소로 삼는 구조로 바꾼다(권장안, §9). 아니라면 지금 클라우드 구조를 유지하고
"인터넷이 끊기면 촬영과 QR 대기만 되고 벽은 마을 배경만 보인다"를 운영 규칙으로 받아들인다.

**Q3. 스태프 로그인을 현장 PIN으로 바꿔도 되나요?** Q2에서 현장 허브를 고르면 사실상 필요하다.

**Q4. 미디어월:** LED인지 프로젝터인지, 실제 입력 해상도(예: 3840×1080), 가로세로 크기(m),
입력 단자, 신호를 보내는 PC(OS, CPU/GPU, 메모리), 관람 거리.

**Q5. 포토부스:** 카메라(웹캠 기종 / 아이패드 / DSLR), 부스 기기(노트북 / 태블릿 / MY4CUT Mini),
조명, 부스 대수.

**Q6. 현장 네트워크:** 교회 와이파이 품질, 유선 랜 가능 여부, 부스·벽·허브를 한 공유기(LAN)에 묶을 수
있는지, 그 공유기를 행사 측이 관리할 수 있는지.

**Q7. 일정과 규모:** 행사 날짜(시작일·종료일), 하루 운영 시간, 운영하는 날 수, 하루 예상 촬영 팀 수.

**Q8. 운영 인력:** 부스 옆 상주 스태프 유무, 검수 담당자 수와 어디서 검수하는지(현장 태블릿 / 원격).

**Q9. 개인정보 (교회 측 결정이 필요):** 사진 보관 기간(행사 종료 후 며칠), QR 링크 유효 시간,
어린이 사진을 벽에 걸 때의 기준(보호자 동의 확인 여부 등), 동의 문구 승인자.

**Q10. 예산:** 클라우드 월 비용 한도, 장비 구매 가능 여부(허브용 미니 PC, 공유기, 프린터).

**Q11. 디자인:** Figma를 쓸지(편집 가능한 원본을 Figma로 만들지, 코드 안 프레임 데이터로 충분한지),
교회·행사 로고 원본 유무, 쓸 폰트(무료 라이선스 폰트로 정해도 되는지).

**Q12. 작업 방식:** 지금 세션은 `main` 브랜치에 바로 올리도록 지정돼 있다. 요청서는 기능별 브랜치와
PR을 원한다. Phase 2부터 기능별 브랜치 + PR로 갈지 확인.

## 9. 권장안 (답을 받기 전 임시 의견)

Q2에 "예"라면 이렇게 가는 것을 권한다. 기존 코드를 최대한 살린다.

- **허브 = 이 Next.js 앱을 현장 미니 PC에서 실행.** 저장은 허브 디스크(SQLite + 사진 파일). 부스와
  벽은 LAN 주소로 허브에 붙는다. 검수·벽·비상 스위치는 인터넷 없이 동작한다.
- **클라우드는 QR 전용 사본.** 허브가 인터넷이 될 때 사진을 Supabase(또는 다른 저장소)로 비동기
  업로드하고, 성공한 사진에만 QR을 띄운다. 가짜 QR 금지 원칙은 그대로다.
- **스태프는 허브의 PIN 로그인.** 감사 기록, 상태 전이 규칙(`lib/ops/moderation.ts`)은 그대로 쓴다.
- **바꾸는 원칙은 문서로 남긴다.** `CLAUDE.md`의 "Supabase가 기준", "스태프 = Supabase Auth", 출력
  관련 항목은 답에 따라 고치고 `docs/DECISIONS.md`에 이유를 적는다.

이 구조에서도 "인터넷이 없으면 QR은 연결이 돌아온 뒤에야 나온다"는 물리적 한계는 남는다.
