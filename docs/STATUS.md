## 흑백 틀 색감 잠금 · iPad mini 4 색감 줄 가림 · 세로 촬영 화면 키우기 (2026-11-27)

사용자 요청 세 가지: "애초부터 흑백 컨셉 이런 템플릿은 필터 고르지 못하게", "필터 고를 때 버튼이 가려지는 오류
수정", "촬영시 카메라 화면이 너무 작아. 키오스크는 세로".

1. 사진이 흑백·세피아인 틀(필름 3컷 전체, 35mm 필름의 흑백·세피아)은 색감 줄이 안 나옴. `frameToneIsFixed`
   (`lib/looks/config.ts`): 줄 숨김, `SET_LOOK` 거절, 최종 사진에도 색감 안 들어감. 35mm 필름 「컬러」와 나머지
   틀은 전과 같음.
2. 원인: Safari 15(iPad mini 4)에는 컨테이너 쿼리가 없어 사진 고르기 격자가 화면 높이 추정값(70vh)으로 커졌다.
   768 × 1024에서 격자가 514 px 높이로 206 px 칸을 넘쳐 색감 줄 제목과 「다음」 버튼을 덮었다(Chromium에서
   컨테이너 규칙을 빼고 재현). 이제 `Stage`(`components/kiosk/stage-size.tsx`)가 그 브라우저에서만 칸 크기를 재서
   `--stage-w` / `--stage-h`로 넘기고, 대체 CSS가 최신 브라우저와 같은 공식으로 크기를 정한다.
3. 세로 화면은 4:3 사진이 폭에 막힌다. 찍히는 범위를 그대로 보여 주는 한(Preview = result) 폭보다 크게는 못
   그린다. 그래서 촬영 칸이 종이 좌우 여백을 넘어 화면 가장자리 작은 틈까지 쓰고, 촬영 전 화면은 안내 두 줄을 한
   줄로 잇고 간격을 줄였다.

## 촬영 중 카메라 화면 키우기 (2026-11-27)

저장되는 사진(최종 합성)은 건드리지 않음. 캐시에 없으면 예전처럼 그 자리에서 그림.

측정: `MEASURE_SMOOTH=1 npx playwright test -c playwright.smooth.config.ts` (Chromium, CPU 4배 느리게,
50 ms 넘는 작업 합계 / 가장 긴 작업, ms). 이 컨테이너에서 1회씩 잰 값. "후"는 아래 두 번 탭 수정까지 넣은 코드.

| ---------------------------- | ---------------- | ---------------- |
| 틀 고르기 들어갈 때, 첫 손님 | 3215 / 3215      | 957 / 957        |
| 틀 고르기 들어갈 때, 둘째    | 1395 / 1395      | 114 / 114        |
| 옵션 화면 6초, 첫 손님       | 1448 / 343       | 809 / 336        |
| 옵션 화면 6초, 둘째          | 1663 / 381       | 57 / 57          |

첫 손님 957은 측정이 페이지를 연 지 3초 만에 시작해서 미리 그리기가 다 끝나지 않은 값이다(미리 그리기는
"화면을 눌러 시작"이 1.5초 조용한 뒤에 시작). 첫 화면에 더 오래 서 있으면 둘째 손님 값에 가까워질 것으로 보지만
측정은 안 함. "사진 확인 → 고르기"의 합계가 늘어난 것은 나머지 색감 7개 × 6장을 뒤에서 미리 그리는 작업이 이 구간에
잡혀서다. 한 조각이 100 ms 이하라 터치를 오래 막지 않는다.

두 번 탭 문제(CI에서 발견, 고침): 처음엔 환영 화면에서도 미리 그렸다. 그림 한 장 동안 손님의 탭이 기다렸다가 두 번
탭 막기(350 ms)를 지나쳐 다음 화면 버튼이 눌렸다(`tablet-matrix` "a double tap…" 실패). 이제 미리 그리기는 "화면을
눌러 시작"에서만 하고, 화면이 바뀐 뒤나 손가락이 닿은 뒤 600 ms 동안은 모든 미리 그리기가 쉰다.

  "QR을 준비하고 있어요"만 나오고 가짜 QR 없음, 다시 붙으면 같은 화면에 QR이 저절로 나옴 / "QR 없이
  다음으로" 후에도 벽 노출 동의가 허브에 기록됨, 개요에 "QR 대기 1건", 연결이 돌아오면 아무도 묻지 않아도

### Phase 4에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: 사진 3000장(3.4 GB)에서 관리자 화면·API 95%가 44 ms 이하, 벽 피드 13 ms, 부스 업로드+동의
  342 ms, 동시 14건 최대 737 ms, 백업 첫 회 22.7초·이후 0.5초. 허브 메모리 220→256 MB.
- 사실: 허브의 쓰기 시간은 사진 수에 비례해 는다(3000장에서 13 ms). 하룻밤 규모에서는 문제없음(추정).
- 사실: 측정 중 `HUB_BACKUP_MINUTES` 를 아주 크게 주면 1 ms마다 백업하던 버그를 찾아 고쳤다(최대 1440분).
- 사실: 미디어월이 허브와 끊기면 잠깐은 그대로, 120초가 지나면 사진 0장, 연결되면 저절로 돌아온다.
  사진이 적으면 120초 전에 빈 줄이 될 수 있다(11장일 때 73초).
- 가정: 측정 기기는 GPU 없는 리눅스 컨테이너다. 현장 노트북과 다르다.
