### 2-5에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: `e2e/cloud.spec.ts`는 허브와 클라우드를 각각 서버로 띄우고, 그 사이 연결을 테스트가 끊고 붙인다.
  통과한 장면: 온라인이면 QR이 클라우드 주소로 나오고 휴대폰 페이지·이미지가 열림 / 클라우드가 끊기면
  "QR을 준비하고 있어요"만 나오고 가짜 QR 없음, 다시 붙으면 같은 화면에 QR이 저절로 나옴 / "QR 없이
  다음으로" 후에도 벽 노출 동의가 허브에 기록됨, 개요에 "QR 대기 1건", 연결이 돌아오면 아무도 묻지 않아도
  백그라운드 작업이 올려 "밀린 일이 없어요"가 됨(약 30초) / 허브에서 삭제하면 클라우드 링크도 404.
- 사실: 허브 파일에 손님 토큰이 남지 않고, 클라우드 사본에는 벽 노출 동의가 없다(E2E에서 두 저장소를
  직접 읽어 확인).
- 사실: 같은 사진을 두 번 올리면 이미 스캔한 QR이 죽기 때문에, QR 요청과 백그라운드 작업이 동시에 와도 한
  번만 올리는지 단위 테스트로 확인했다.
- 검증됨(CI): 클라우드가 Supabase일 때 허브 사본 재발급·삭제. 공통 계약 테스트가 PR #12의 CI "Supabase
  integration (local stack)" 작업에서 통과했다. 이 세션에는 Docker가 없어 직접 돌리지는 않았다.
- 미검증: 실제 인터넷 너머(현장 공유기 → Vercel). 배포가 있어야 한다(막힘, 아래 "배포").
- 정해야 할 것: 클라우드 사본 보관 기간. 링크 유효 기간에 맞춰 짧게 두는 것을 제안한다(기획안: 링크
  24시간). 교회 개인정보 결정(10/16) 뒤에 확정한다.

### 2-1b에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: 가상 시계 테스트(`tests/unit/hub-retention.test.ts`)에서 벽에 안 나간 사진은 촬영 24시간 1분
  전에는 남고 1분 뒤에는 지워졌다. 승인·숨김 사진은 3일 뒤에도 남고 행사 종료 + 24시간에 지워졌다.
  `PHOTO_RETENTION_DAYS` 상한은 벽 사진에도 적용됐다. 지울 때 이미지 파일과 링크가 함께 사라지고
  `system / retention_delete`로 감사 기록이 남았다. 450장 밀린 것도 한 번에 처리했다.
- 사실: 인터넷이 끊긴 채 보관 작업이 돌아도 클라우드 호출을 하지 않고 삭제 대기로만 쌓는다. 연결되면
  동기화 작업이 보낸다(같은 테스트).
- 미검증: 실제 노트북에서 며칠 켜 두고 끄고 하면서 도는 것. 리허설 때 본다.
- 정해야 할 것: `EVENT_END_AT`(행사 종료 시각). 설정 전에는 벽 사진도 촬영 30일 뒤 삭제된다.

### 2-2b에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: E2E에서 0.8초 누르면 열리지 않고 3.3초 누르면 열렸다. 틀린 PIN은 거절, 맞는 PIN이면 메뉴가 열리고
  부스 브라우저에 스태프 쿠키가 생기지 않았다. "처음으로"는 진행 중이던 촬영을 첫 화면으로 돌렸다.
- 사실: 부스에서 틀린 PIN 5번이면 그 사람은 관리자 로그인도 429로 막힌다(같은 한도, API 테스트).
- 미검증: 실제 터치 화면에서 길게 누르기. 마우스로만 시험했다. 터치 기기가 정해지면(막힘 "터치 입력")
  리허설에서 확인한다. 브라우저가 길게 누르기를 우클릭 메뉴로 바꾸지 않도록 막아 두었다.

### 2-6에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실(리눅스 컨테이너에서 직접 실행): `scripts/hub-start.mjs`가 허브를 켜고 LAN 주소를 출력했다.
  서버 프로세스를 강제로 죽이자 약 2초 뒤 새 프로세스로 다시 떴다. 두 번째로 실행하면 "이미 켜져
  있어요"만 출력하고 끝났다. 켠 지 1분 뒤 USB 폴더에 첫 백업이 생겼다. 종료 신호에 서버까지 함께 꺼졌다.
- 사실(단위·API 테스트): 백업은 바뀐 파일만 복사하고, 허브에서 지운 사진은 다음 백업에서 지운다. USB
  폴더가 없으면 노트북에 쓰지 않고 실패하며 개요에 이유가 나온다. 복구는 기존 데이터를 옆으로 옮기고
  사진·이미지를 되살린다.
- 미검증: Windows `.bat`/`.ps1`, macOS `.command`. 이 환경에는 둘 다 없다(`.command`는 bash 문법 검사만
  했다). Chrome 키오스크 창 띄우기도 실제 화면에서 본 적 없다. 노트북이 정해지면 RUNBOOK 10번대로
  설치하면서 확인한다.

### 2-4에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: LED 해상도를 몰라서 장면이 화면 비율에 맞춰 사진 수를 정하도록 만들었다(D61). 헤드리스 Chromium에서
  1920×1080(3장), 3840×1080(8장), 3840×2160(3장), 4000×1000(9장)을 실제 승인 사진으로 열어 기대한 수가
  걸리는 것을 확인하고 스크린샷을 남겼다(`docs/screenshots/wall-*.jpg`). 사진 중 2장은 부스 흐름(모의
  카메라)으로, 나머지는 시험용 이미지로 만들었다.
- 사실: 벽에는 640px 썸네일 대신 긴 변 1400px 사본이 간다(E2E에서 이미지 높이 > 640 확인). 사진을 지우면
  이 사본도 지워진다(계약 테스트, Supabase는 CI).
- 미검증: 실제 LED와 관람 거리에서 얼굴이 알아볼 만한지. 막힘(LED 사양·현장 시험).
- 미검증: 12시간 이상 구동 시 메모리·프레임. Phase 4에서 측정한다.

### 2-4b에서 확인한 것 (2026-10-13, 이 세션에서 실행)

- 사실: 관리자 첫 화면에서 "끄기"를 누르면 벽이 15초 안에 "오늘의 미디어월은 여기까지예요"로 바뀌고 사진이
  모두 내려갔다. "자동"으로 되돌리면 사진이 다시 걸렸다. 감사 기록에 남았다(E2E).
- 사실: 운영 시간 밖에는 피드에 사진 id가 하나도 없고 이미지 요청도 404다. 다시 여는 시각을 벽에 알려 준다
  (API 테스트). 자정을 넘기는 시간, 한국 시간 기준 계산은 단위 테스트로 확인했다.
- 미검증: Supabase 마이그레이션(`20261013090000_phase2_wall_hours.sql`)은 CI의 Supabase 작업에서만 돈다.
- 정해야 할 것: 실제 운영 시간(담당자와 정한다고 하셨음). 정하기 전에는 언제나 켜져 있다.
