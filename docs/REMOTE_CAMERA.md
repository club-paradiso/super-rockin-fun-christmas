# 원격 카메라 모드 (Remote Camera) — 아이폰을 부스의 후면 카메라로

결정: `docs/DECISIONS.md` D100. 상태 표기는 **구현됨 / 검증됨 / 미검증 / 막힘** 네 가지만 쓴다.
봉사자용 한 장 안내: `docs/REMOTE_CAMERA_GUIDE_KO.md`.

**이 문서가 증명하지 않는 것:** iPhone 12와 iPad mini 4 실기기에서 돌려 본 적이 없다. 아래 "검증됨"은
전부 Node(Vitest)와 헤드리스 Chromium(Playwright)에서 나왔다. 실기기에서 확인할 목록은 10절이다.
"운영 가능(production ready)"이라고 부르지 않는다.

## 1. 한눈에

```
 [아이패드 mini 4 · Safari]  손님이 만지는 화면                  [아이폰 12 · Safari]  케이스 안쪽, 후면 카메라가 손님을 봄
  /kiosk?camera=remote                                             /camera/remote
  RemoteCamera (lib/camera/remote-camera.ts)                       PhoneCamera (lib/remote-camera/phone.ts)
        │  ① offer / ICE  ───────── HTTPS 우편함 (/api/kiosk/camera/signal ⇄ /api/camera/signal) ─────────►  │
        │  ◄───────── answer / ICE ───────────────────────────────────────────────────────────────────────  │
        │                                                                                                   │
        │  ② WebRTC (같은 Wi-Fi면 직접, 아니면 STUN/TURN)                                                    │
        │     · 영상: 폰 → 패드, ≈720p 미리보기                                                              │
        │     · 데이터 채널 "ftl": CAPTURE_REQUEST → CAPTURE_STARTED → CAPTURE_RESULT + 사진 조각들 → CAPTURE_ACK │
        ▼                                                                                                   ▼
  기존 부스 흐름: 카운트다운 → 촬영 → 검토 → 틀 → 동의 → QR       (사진은 서버를 거치지 않는다)
```

손님은 아이패드만 만진다. 아이폰은 설치 때 코드 입력과 "카메라 시작" 한 번, 그 뒤로는 만질 일이 없다.

## 3. 어떻게 동작하나

### 3.1 연결 (WebRTC)

1. 부스가 시작 단계(`camera` 화면)에서 `GET /api/kiosk/camera/status`로 "이 부스에 짝 카메라가 있고 15초 안에
   신호가 있었나"를 본다. 없으면 `missing` 오류 화면(기존 "카메라를 찾을 수 없어요").
2. 부스가 offer(영상 수신 전용 + 데이터 채널 `ftl`)를 만들어 우편함에 올린다. 아이폰 페이지는 평소 1.5초
   간격으로 우편함을 읽다가(연결 중에는 0.7초) offer를 받아 자기 후면 카메라 트랙을 붙여 answer를 올린다.
3. ICE 후보도 같은 우편함으로 오간다(trickle). 연결 시간 제한 10초, 안에서 최대 2번 시도(1초 쉬었다가).
4. 데이터 채널이 열리고 폰이 `CAMERA_READY`(실제 카메라 해상도·화질 모드)를 보내면 부스가 `ready`로 넘어간다.
   그 뒤 우편함 폴링은 멈춘다. 이후는 하트비트(2초)로 서로 살아 있음을 확인하고, 7초 동안 아무 소리가 없으면
   끊긴 것으로 본다.

한 번 켜진 우편함 메시지는 서버에 2분만 남는다. 서버는 영상도 사진도 보지 않는다.

### 3.2 미리보기와 사진은 별개

- **미리보기:** 폰은 카메라 피드를 `scaleResolutionDownBy`로 ≈1280×960, 24fps, 1.5 Mbps 이하로 줄여 보낸다
  (iPad mini 4의 A8이 감당하는 수준). Safari가 이 설정을 무시해 큰 영상을 보내면(연결 3초 뒤 `getStats`의
  `frameWidth`로 확인) 폰이 트랙을 미리보기 크기로 낮추고, 촬영 순간에만 풀 해상도로 올렸다 되돌린다(대체
  전략 — **실기기 미검증**).
- **사진:** 폰의 카메라 피드는 화질 모드에 맞춰 열린다(`hq` 4032×3024 희망, `standard` 1920×1440, `eco`
  1280×960 — `getUserMedia`의 `ideal`이라 브라우저가 가장 가까운 값을 고르고, 실제 값은 관리자에 보인다).
  촬영 요청이 오면 그 피드의 현재 프레임을 캔버스에 그려 부스가 요청한 비율(`captureAspect` 4:3)로 중앙을
  잘라(늘리지 않음) 요청된 최대 너비(`captureMaxWidth` 1600) 이하로 줄이고 JPEG로 인코딩한다. 원본이 작으면
  **키우지 않는다.** 부스는 받은 JPEG를 기존 `grabFrame`에 넣어 좌우 반전만 적용한다. 그래서 미리보기와
  결과가 같은 규칙(`KIOSK_CONFIG.mirror`, `captureAspect`)을 따른다.
- `ImageCapture.takePhoto`는 쓰지 않는다. iOS Safari에 없고(Chromium 계열에만 있음), 있어도 방향 처리가
  달라 위험하다. WebP 인코딩도 Safari의 `canvas.toBlob`이 지원하지 않아(PNG로 떨어짐) JPEG만 쓴다.
- 풀 12MP(4032×3024) 사진이 나온다고 가정하지 않는다. 실제 화소는 기기와 iOS가 정한다.
  기존 합성(1200×3600 스트립)은 1600px 컷으로 충분하다. 더 큰 컷이 필요하면 `captureMaxWidth`를 올리되
  iPad mini 4의 메모리(컷 6장이 캔버스로 남는다)를 먼저 재 본다.

### 3.3 리모컨 셔터 프로토콜

한 개의 순서 보장·신뢰성 데이터 채널에 JSON 제어 메시지(문자열)와 사진 조각(바이너리)이 같이 흐른다.

| 메시지                           | 방향    | 뜻                                                                                     |
| -------------------------------- | ------- | -------------------------------------------------------------------------------------- |
| `CAMERA_READY`                   | 폰→패드 | 채널이 열렸고 카메라가 준비됨. 해상도·모드 포함                                        |
| `CAPTURE_REQUEST`                | 패드→폰 | **고유 id**, 비율·최대 너비·JPEG 품질. `resend:true`면 같은 사진을 다시 보내 달라는 뜻 |
| `CAPTURE_STARTED`                | 폰→패드 | 요청을 받았고 찍는 중                                                                  |
| `CAPTURE_RESULT`                 | 폰→패드 | 길이·조각 수·CRC-32·크기·인코딩 시간. 바로 뒤에 바이너리 조각들                        |
| `CAPTURE_FAILED`                 | 폰→패드 | 이유 코드(`busy`·`not_ready`·`frozen_source`·`hidden`·`encode_failed`·`unsupported`)   |
| `CAPTURE_ACK`                    | 패드→폰 | 검증을 마쳤다. 부스가 잰 총 시간·전송 시간 포함. 폰은 그 사진을 메모리에서 지운다      |
| `HEARTBEAT`                      | 양방향  | 2초마다                                                                                |
| `RECONNECT_REQUEST`/`DISCONNECT` | 양방향  | 이쪽을 끊고 새로 연결하자 / 끊는다                                                     |

규칙(전부 `tests/unit/remote-shutter.test.ts`에서 확인):

- 한 번에 한 컷. 부스는 진행 중이면 `busy`로 거절하고, 폰도 다른 id가 오면 `busy`로 답한다.
- **같은 id는 한 번만 찍는다.** 중복 요청은 새로 찍지 않고(이미 찍는 중이면 무시, 끝났으면 캐시된 같은 사진을
  다시 보냄). 부스가 ACK한 id는 사진을 지우고 이후 요청을 무시한다. 폰의 캐시는 60초, 메모리에만 있다.
- 사진은 16 KiB 조각 `[전송 id][번호][총수][내용]`으로 나가고, 채널 버퍼가 256 KiB를 넘으면 `bufferedamountlow`까지
  기다린다(역압). 4초 동안 진전이 없으면 전송 실패.
- 부스는 길이와 CRC-32가 맞아야 받아들인다. 어긋나면 **같은 id로** 다시 보내 달라고 하고(새로 찍지 않음) 최대
  2번까지. 그래도 안 되면 `corrupt`로 실패한다. 재전송마다 전송 id가 새로 붙어 이전 시도의 조각이 섞이지 않는다.
- 시간 제한: 시작 응답 2.5초, 요청부터 검증된 사진까지 8초. 늦게 온 결과는 절대 쓰지 않는다(id가 현재
  요청과 같아야 한다).
- 폰은 찍기 전에 페이지가 가려졌는지(`hidden`), 트랙이 끊기거나 음소거됐는지(`frozen_source`), 비디오 재생 시간이
  지난번 사진과 같은지(`frozen_source`)를 본다. 하나라도 걸리면 실패이고 **이전 프레임을 다시 쓰지 않는다.**
- 실패는 기존 부스 상태 머신이 그대로 처리한다: 같은 컷의 카운트다운을 다시 시작, 3번 연속 실패하면 카메라 오류
  화면. 이미 찍은 컷은 유지된다(`BEGIN_SHOOTING`이 첫 빈 칸부터 이어 감).

**카운트다운과의 동기화:** 요청은 카운트다운이 0이 되어 `capturing` 단계가 시작될 때 나간다(기존
`capturing` 효과 안). 폰은 요청을 받은 그 순간의 프레임을 쓴다. 지연은 `start`(요청→STARTED, 약 네트워크 왕복),
`encode`(폰의 인코딩), `transfer`(결과→마지막 조각), `total`로 잰다. 부스는 `RemoteCamera.metrics`에 두고, ACK로
폰에 알리고, 폰이 5초마다 관리자에 보고한다.

### 3.4 끊김과 복구

| 상황                               | 부스(패드)                                                                                    | 폰                                                                                             |
| ---------------------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 폰 Wi-Fi 끊김 / 폰 페이지 새로고침 | 하트비트 7초 또는 채널 close로 감지 → `CAMERA_FAILED` → "카메라를 찾을 수 없어요" + 다시 시도 | 오류 코드 보고, 우편함 폴링 계속(지수 백오프 1→10초)                                           |
| 패드 Wi-Fi 끊김                    | 같음. 업로드 큐(IndexedDB)는 기존대로 동작                                                    | 링크 끊김 감지 → `대기 중`으로 돌아가 새 offer를 기다림                                        |
| 미리보기 정지                      | `isStalled()`(트랙 음소거 또는 4초간 새 프레임 없음) → 기존 복구 로직이 재시작                | —                                                                                              |
| Safari 백그라운드·화면 잠금        | —                                                                                             | `backgrounded` 보고, 돌아오면 트랙을 확인해 필요하면 카메라를 다시 켬(최대 5번, 1→15초 백오프) |
| 카메라 권한 거부                   | 관리자에 `permission_denied`. 사진은 안 찍힌다                                                | 설정 안내 표시                                                                                 |
| 사진 전송 시간 초과·손상           | 재전송(같은 id) 또는 실패 → 같은 컷 재시도                                                    | 캐시 유지                                                                                      |
| 중복 촬영 명령                     | —                                                                                             | 한 번만 찍음                                                                                   |
| 세션 복원                          | 부스 새로고침: 기존 동작(처음 화면). 폰 새로고침: 쿠키가 남아 있어 "카메라 시작"만 다시 누름  | —                                                                                              |
| 복구 실패                          | 오류 화면이 계속 남고 "처음으로"로 나갈 수 있음                                               | 5번 실패하면 멈추고 관리자에 오류가 남음. 스태프가 폰을 봐야 함                                |

주의: **아이폰이 잠기면 카메라는 멈춘다.** 잠금 상태에서 촬영된다고 주장하지 않는다. 그래서 자동 잠금 끔,
충전, 안내 접근(Guided Access)이 필수다(6절).

## 4. 페어링과 보안

- **코드:** 스태프가 `/admin/remote-camera`에서 키오스크를 고르고 "연결 코드 만들기"를 누르면 서버가 CSPRNG로
  8자(31자 알파벳, 0/O/1/I/L 없음, 약 8.5×10¹¹ 가지)를 만든다. 서버에는 SHA-256 해시만 남는다. 10분, 1회용.
  같은 키오스크의 이전 미사용 코드는 즉시 죽는다. 화면에는 QR(`/camera/remote?code=…`)과 코드가 같이 나온다.
- **교환:** 아이폰이 `POST /api/camera/link`로 코드와 이름을 보내면 서버가 원자적으로 코드를 소모하고(두 번째는
  실패) 그 키오스크의 이전 짝을 해제한 뒤 새 짝을 만든다. 응답은 `ftl_camera` 쿠키(HttpOnly, SameSite=Lax, https면
  Secure, 30일). 틀린·만료·사용된 코드는 모두 같은 400이다. IP당 10분 10회, 전체 10분 60회로 제한한다. 주소창의
  `code`는 읽는 즉시 지운다.
- **쿠키:** `c1.<짝 id>.<키오스크 id>.<만료>.<MAC>`. MAC 키는 `KIOSK_SESSION_SECRET`과 `KIOSK_ENROLL_SECRET`
  두 값으로 따로 파생한다(라벨 `ftl-remote-camera-v1`). 부스 쿠키·관리자 쿠키·카메라 쿠키는 서로 대신할 수 없다.
  서명이 맞아도 짝이 해제됐으면 매 호출마다 거절한다(해제는 즉시 효력).
- **관리자:** 기존 인증(공용 비밀번호 D84 또는 스태프 로그인)을 그대로 쓴다. 새 관리자 비밀번호 없음.
  모든 변경 요청은 same-origin + JSON이다. 폰이나 부스는 관리자 명령(`cmd`)을 우편함에 올릴 수 없다(프로토콜이 거절).
- **공개 접근 없음:** `/camera/remote` 페이지 자체는 공개 HTML이지만 코드 없이는 아무것도 하지 못하고 어느 부스의
  정보도 보여 주지 않는다. 시그널링·상태 API는 부스 쿠키 또는 카메라 쿠키가 필요하다.
- **개인정보:** 얼굴 인식·생체 정보·소리 녹음·공개 스트리밍 없음. 마이크는 요청하지 않는다(`audio:false`).
  영상·사진은 폰 → 패드로만 가고 서버는 숫자와 고정 코드(`CameraReport`)만 받는다. 로그에는 코드·쿠키·사진이 없다
  (이벤트 `camera_paired`, `camera_revoked`, `camera_command`는 키오스크 id와 짝 id만). 관리자의 "테스트 촬영"은
  160px 썸네일(≤14 KB)을 만들어 상태에 담고, 서버가 2분 뒤 지운다. **손님 사진은 어디에도 남지 않는다.**
- **전송 암호화:** 시그널링은 https. WebRTC는 DTLS-SRTP/DTLS 데이터 채널로 기본 암호화된다. CRC-32는 손상 점검용이지
  보안 해시가 아니다(위조 방지는 DTLS와 페어링이 맡는다).
- **감사:** 짝 지음·해제는 짝 행(`paired_by`, `created_at`, `revoked_by`, `revoked_at`)과 구조화 로그에 남는다. 사진·검수
  상태는 건드리지 않으므로 기존 감사 표에는 넣지 않았다(D100).
- **끄기:** `REMOTE_CAMERA_DISABLED=1` → 모든 원격 카메라 경로가 404.

## 5. 네트워크 요구 사항 (솔직한 한계)

- 아이폰 Safari의 카메라(`getUserMedia`)는 **보안 출처(https)** 에서만 켜진다. 부스와 폰 페이지는 **같은 출처**여야
  우편함을 공유한다. 현실적으로 **https 클라우드 주소**(`PUBLIC_BASE_URL`)를 쓴다.
  `http://<허브 IP>:3000`은 폰에서 카메라가 안 켜진다(관리자·폰 페이지가 경고한다). 허브를 쓰려면 모든 기기가
  신뢰하는 자체 서명 https가 필요하다(`docs/ARCHITECTURE.md` 1.4의 C안).
- 코드 입력·시그널링(연결을 만드는 몇 초)은 **인터넷이 필요하다.** 일단 연결되면 같은 Wi-Fi에서는 영상과 사진이
  폰↔패드로 직접 간다. 이 상태에서 인터넷이 끊겨도 이미 열린 채널은 유지될 수 있지만, **끊긴 뒤 다시 연결하는 것은
  인터넷이 있어야 한다.** 완전 오프라인 동작을 주장하지 않는다.
- 같은 Wi-Fi: iOS Safari는 로컬 IP를 mDNS 이름(`xxxx.local`)으로 가린다. 대부분의 가정·사무실 공유기에서 같은 LAN
  기기끼리는 풀리지만 **미검증**이다.
- STUN은 기본으로 `stun:stun.cloudflare.com:3478`(무료). 다른 값은 `REMOTE_CAMERA_ICE_SERVERS`(JSON)로 바꾼다.
- **TURN은 기본으로 없다.** "클라이언트 격리(AP isolation)"가 켜진 공용 Wi-Fi, 폰은 셀룰러·패드는 Wi-Fi인 경우처럼
  직접 연결이 막히면 연결이 실패한다. 이때는 TURN 서버(예: 운영자 자신의 coturn, 무료 티어 서비스)를 구해
  `REMOTE_CAMERA_ICE_SERVERS`에 넣어야 한다. 비용 최소 원칙에 따라 기본은 켜지 않았다.
  **권장:** 두 기기를 같은 전용 공유기에 붙이고 클라이언트 격리를 끈다.
- 시그널링 폴링 부하: 대기 중 폰은 1.5초마다 1회(분당 40회), 연결 중 부스는 0.35초마다 몇 초 동안. Vercel 함수
  호출 수는 늘지만 무료 한도에서 문제가 되는 수준은 아니라고 **추정**한다(측정 안 함). Supabase 쪽은 `touch`를 4초에
  한 번만 쓴다.

## 6. 설치·운영 가이드

### 6.1 한 번만 하는 일 (운영자)

1. 마이그레이션 `20261116090000_remote_camera.sql`을 Supabase에 적용한다(클라우드 사용 시). **적용 전에는 코드가
   Supabase를 못 찾아 원격 카메라 경로만 500을 낸다**(부스·QR·검수는 영향 없음). 적용은 사람이 한다.
2. (선택) `REMOTE_CAMERA_ICE_SERVERS`, 끄려면 `REMOTE_CAMERA_DISABLED=1`.
3. 아이패드 Safari에서 부스 주소를 `…/kiosk?camera=remote`로 열고 홈 화면에 추가한다(주소의 `?camera=remote`가
   바로가기에 저장된다). 또는 빌드 변수 `NEXT_PUBLIC_CAMERA_MODE=remote`.

### 6.2 현장 설치

- **기기:** 아이패드 mini 4(iPadOS 15, 부스 화면), 아이폰 12(후면 1x 광각). 둘 다 같은 Wi-Fi, 둘 다 충전 연결.
- **아이패드:** 설정 → 디스플레이 → 자동 잠금 안 함, 안내 접근(Guided Access)으로 Safari 고정, 밝기는 실내에 맞게(밝을수록
  발열), 홈 화면 바로가기로 전체 화면.
- **아이폰:** 설정 → 디스플레이 및 밝기 → 자동 잠금 **안 함**. Safari에서 운영 주소의 `/camera/remote` 열기 → 코드 입력 →
  "카메라 시작" → 카메라 허용. 화면은 "화면 어둡게"를 눌러 두면 밝기·발열이 줄어든다. 그 다음 설정 → 손쉬운 사용 →
  안내 접근을 켜고 이 페이지에서 시작한다(실수로 앱을 나가는 것을 막는다). 안내 접근은 잠금 화면과는 별개다: **자동
  잠금이 켜져 있으면 안내 접근 중에도 화면이 잠긴다.**
- **장착 위치(권장, 현장에서 조정):** 아이폰은 아이패드 화면 바로 위 중앙, 후면 카메라 렌즈가 손님의 얼굴 높이를 향하게
  케이스 안쪽에 고정한다. 높이는 손님 눈높이 약 150~160 cm가 기준이다. 렌즈 앞에 반사되는 케이스 유리가 없어야 한다.
  아이폰 화면은 손님 반대쪽(케이스 안)을 본다. 가로로 세우면 4:3 컷의 손실이 적다. 한 번 맞춘 뒤에는 "테스트 촬영"으로
  구도를 확인하고 손님이 선 자리에서 머리·어깨가 들어오는지 본다.
- **케이블·열:** 충전 케이블은 케이스 뒤에서 아이패드·아이폰 각각 인출, 당기는 힘이 단자에 걸리지 않게 고정. 두 기기 모두
  통풍구가 필요하고 아이폰은 카메라+인코딩+충전으로 뜨겁다. 한 시간 단위로 손으로 온도를 확인하고, 뜨거우면 관리자에서
  화질 모드를 `표준`이나 `절전`으로 낮춘다(발열로 iOS가 카메라를 끄기 전에).
- **방문객이 볼 수 있는 것:** 아이폰 화면은 손님이 볼 수 없는 쪽이고, 디버그 화면은 폰에만 있다. 카메라 전환은 손님이
  할 수 없다(관리자의 `화질 모드`로만).

### 6.3 하루 시작·끝

시작: ① 두 기기 충전 연결·화면 켬 ② 아이폰 Safari에서 `/camera/remote`가 "대기 중"인지 ③ `/admin/remote-camera`에서
상태 `대기 중`/마지막 신호 몇 초 전 ④ 테스트 촬영(썸네일이 뜨는지) ⑤ 부스에서 한 번 끝까지(QR까지) 찍어 본다.
끝: 부스를 처음 화면으로 두고, 아이폰은 "연결 해제" 하지 말고 충전을 유지하거나 끈다. 이벤트가 끝나면 관리자에서
"페어링 해제".

### 6.4 관리자 `원격 카메라 관리`

카메라 이름 · 짝 키오스크 · 연결 상태(연결 안 됨/대기 중/연결 중/연결됨/문제 있음) · 마지막 신호 · 미리보기 해상도 · 실제 촬영
해상도 · 화질 모드 · 최근 촬영 지연(전송·인코딩 분해) · 자동 복구 횟수 · 오류 메시지(고정 코드를 한국어로) · 버튼: 연결 코드
만들기, 테스트 촬영(2분간 썸네일), 재연결(카메라 재시작+링크 닫기), 연결 끊기(링크만 닫음), 화질 모드, 페어링 해제(확인 창).
미리보기 영상은 관리자에 **넣지 않았다**: 두 번째 영상 스트림이 폰 발열과 아이패드 부하를 키우기 때문이다.
대신 테스트 촬영 썸네일이 가벼운 확인 수단이다.

## 8. 롤백

1. 가장 빠름: 부스 주소에서 `?camera=remote`를 지운다(홈 화면 바로가기를 다시 만든다). 부스는 그 자리에서 일반
   웹캠(`BrowserCamera`)으로 돌아간다. 원격 카메라 코드는 쓰이지 않는다.
2. 서버에서 끄기: `REMOTE_CAMERA_DISABLED=1`로 재배포하면 모든 원격 카메라 경로가 404가 된다.
3. 폰 정리: 관리자에서 "페어링 해제". 마이그레이션은 **되돌리지 않아도 된다**(테이블은 독립이고 비어 있다). 지우려면
   `drop table public.remote_camera_signals, public.remote_camera_pairings, public.remote_camera_codes cascade; drop function public.ftl_camera_consume_code(text, uuid, text, timestamptz);`
4. PR을 되돌리면 기존 부스는 영향이 없다(새 파일이 대부분이고 `lib/camera/index.ts`, `types.ts`, `admin-nav.tsx`만 바뀜).

## 10. 알려진 한계와 실기기에서 꼭 확인할 것

사람이 실기기에서 채우기 전까지 아래는 모두 **미검증**이다 (`docs/DEVICE_ACCEPTANCE.md`에 같은 항목을 R 시리즈로 추가).

- **막힘 가능성: iPad mini 4(최대 iPadOS 15.8)에서 부스 앱 자체가 돌아가는지.** 원격 카메라 코드는 Safari 15 API 점검
  (`tests/unit/remote-compat.test.ts`)을 통과하고 대체 경로가 있다. 그러나 **기존 앱이 그 대상이 아니다.** 이 세션에서 프로덕션
  빌드를 검사했다(측정, 실기기 아님):
  - JS: Next 16 런타임에 ES2022 `static {}` 블록(Safari 16.4+)이 들어 있다. `es-check es2021`은 번들 25개 중 4개에서 실패하고
    `es2022`는 통과한다. Safari 15.x는 이 구문을 파싱하지 못할 수 있다(= 페이지가 아예 안 뜰 수 있음).
  - CSS: Tailwind 4가 만든 CSS에 `@property` 48곳, `color-mix()` 135곳, `oklch()` 40곳, `@layer` 5곳(Safari 16.4 기준 기능)이 있고, 부스 레이아웃의
    컨테이너 쿼리(`container-type`, Safari 16+)는 `@supports`로 보호돼 있어 꺼지면 대체 레이아웃으로 간다.
  - 판단: **iPad mini 4에서 부스가 뜬다는 증거가 없고, JS 쪽은 실패할 가능성이 높다.** 해결 후보(사용자 결정): (a) 먼저 기존 부스를
    iPad mini 4에서 열어 본다(`DEVICE_ACCEPTANCE.md` A) (b) `package.json`에 `browserslist`(예: `ios_saf >= 15`)를 넣어 구문을 낮춘다 —
    전체 빌드가 바뀌므로 전체 E2E와 실기기 확인이 다시 필요하다 (c) 부스 화면은 iPadOS 16.4 이상이 되는 아이패드(예: 이미 대상인 iPad Air 4)를
    쓰고 mini 4는 예비로 둔다. 이 PR은 (b)를 적용하지 않았다.

- iPhone 12 Safari: 후면 카메라 선택(`facingMode: environment`는 "이상적" 요구라 전면으로 떨어질 수 있고, 폰 페이지가
  `후면 카메라: 아니요`로 알린다), 실제로 얻는 해상도(4032×3024 요청이 어디까지 되는지), 렌즈를 지정하지 못함, 권한 프롬프트,
  `scaleResolutionDownBy` 적용 여부(대체 전략 동작), 발열 시간, 백그라운드·잠금에서의 카메라 정지와 복귀, 안내 접근과의 상호작용.
- iPad mini 4 (iPadOS 15) Safari: WebRTC 수신·디코딩 부하, 데이터 채널 binary 안정성, 6컷 캔버스 메모리, 장시간 가동, 터치.
  `createImageBitmap(Blob)`이 iPadOS 15.0에서 불안정하면 `<img>` 대체 경로가 있다(`lib/remote-camera/media.ts`) — 미검증.
- Wi-Fi: 클라이언트 격리·mDNS·NAT. TURN 필요 여부. 연결까지 걸리는 시간.

- 사진 해상도는 `captureMaxWidth`(1600)에 맞춘다. 더 높이려면 아이패드 메모리를 실측한 뒤에.

  연결 유지가 필요하고 무료 한도가 있다 — 이번엔 채택하지 않았다.
