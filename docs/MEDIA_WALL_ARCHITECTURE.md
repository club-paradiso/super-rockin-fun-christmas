# 미디어월 전용 주소 — 구조 (D68)

## 1. 결론

**같은 앱, 같은 배포, 두 번째 호스트 이름.** `WALL_HOSTS`에 적은 주소로 들어오면 `/`가 미디어월이고,
부스·관리자·방문객 페이지는 부스 주소로 넘어간다. 별도 코드베이스·Vercel 프로젝트·데이터베이스는
만들지 않았다.

| 용도                | 주소                                                                | 상태                                              |
| ------------------- | ------------------------------------------------------------------- | ------------------------------------------------- |
| 포토부스·관리자     | `https://follow-the-lights.vercel.app`                              | 기존 (미리보기 배포)                              |
| 미디어월 (클라우드) | 예: `https://follow-the-lights-wall.vercel.app` → `/`가 곧 미디어월 | **코드 구현됨, 주소 연결은 승인 대기** (아래 4절) |
| 미디어월 (현장)     | `http://<허브 LAN 주소>:3000/wall`                                  | 기존. 인터넷 없이 동작                            |

## 2. 두 안 비교 (요구사항 4.1)

| 기준          | A. 같은 앱 + 호스트 라우팅 (채택)                       | B. 별도 Vercel 프로젝트/프런트엔드                  |
| ------------- | ------------------------------------------------------- | --------------------------------------------------- |
| 안정성        | 기존 렌더러·스케줄러를 그대로 씀, 새 코드 경로 최소     | 같은 렌더러를 복사하거나 패키지로 빼야 함           |
| 장애 격리     | 프런트 배포는 하나. 백엔드 장애는 어느 쪽이든 벽을 멈춤 | 프런트만 격리. 백엔드·DB 공유라 실제 격리 효과 작음 |
| 유지보수      | 한 곳                                                   | 두 곳 (환경변수·비밀값·배포 이중)                   |
| 데이터 일관성 | 같은 피드·같은 규칙                                     | 같지만 API 버전 엇갈림 위험                         |
| 보안          | 키오스크 쿠키는 호스트별 → 벽 주소 등록은 별도 세션     | 같음 + 교차 출처 API 설계 필요                      |
| 배포          | 도메인 하나 추가 + `WALL_HOSTS`                         | 프로젝트 생성·연결·빌드 설정                        |
| Vercel 사용량 | 추가 빌드 없음, 미들웨어 없음(빌드 시 rewrite)          | 빌드 2배                                            |
| 비용          | 0 (vercel.app 하위 주소)                                | 무료 한도 안이어도 관리 부담                        |
| 현장 오프라인 | 허브 `/wall` 그대로                                     | 허브에는 해당 없음                                  |
| 실시간 동기화 | 기존 5초 폴링 그대로                                    | 같음                                                |

## 3. 동작

- `next.config.ts`가 빌드 때 `WALL_HOSTS`(쉼표 구분)와 `PUBLIC_BASE_URL`을 읽는다(`lib/wall/host.ts`).
  - 벽 호스트의 `/` → `/wall` (rewrite, 주소창은 그대로)
  - 벽 호스트의 `/admin`, `/admin/*`, `/kiosk`, `/m/*`, `/p/*` → 부스 주소로 임시 리다이렉트
  - `/wall`, `/api/wall/*`, `/api/kiosk/heartbeat`, `/kiosk/enroll`, `/api/kiosk/enroll`, 정적 파일은 그대로
- 호스트 비교는 정확 일치 정규식(`^wall\.example\.org$`) → `evil-wall.example.org` 등은 해당 없음.
- 미들웨어(proxy.ts)를 넓히지 않았다 → 요청마다 추가 함수 호출 없음.
- 벽 기기 인증: 벽 주소에서 `/kiosk/enroll?next=wall`로 등록. 쿠키가 그 호스트에만 있으므로 부스
  주소에서 쓸 수 없고, 관리자 → 키오스크에서 따로 해제할 수 있다.

## 4. 주소 연결 — 남은 마지막 단계 (승인 필요, 실행하지 않음)

프로덕션 설정 변경이라 이 작업에서는 하지 않았다. 확인한 사실: Vercel 프로젝트
`follow-the-lights`(prj_dhd55IH2RtWnevBn0ZyAukp1YGYn)에는 지금 `follow-the-lights.vercel.app` 하나만
연결돼 있다(2026-11-08, Vercel API 읽기). `follow-the-lights-wall.vercel.app`이 비어 있는지는 이
세션의 네트워크 정책 때문에 직접 열어 보지 못했다 — **미검증**.

1. Vercel → 프로젝트 `follow-the-lights` → Settings → Domains → `follow-the-lights-wall.vercel.app` 추가
   (이미 다른 프로젝트가 쓰면 거절된다 → 다른 이름 선택)
2. Settings → Environment Variables → `WALL_HOSTS=follow-the-lights-wall.vercel.app` (Production·Preview)
3. 다시 배포 (rewrite는 빌드 때 정해진다)
4. 확인: `https://follow-the-lights-wall.vercel.app/` → "이 화면은 아직 미디어월로 등록되지 않았어요",
   `/admin` → 부스 주소의 관리자 로그인으로 이동

## 5. 실시간 갱신·장애

기존 구조 그대로(평가 결과 바꿀 이유 없음):

- 5초 폴링, 동시에 하나만, 8초 시간 초과(AbortController). 숨김·삭제는 다음 폴링에서 내려감(≤ 5초).
- 피드에 없는 사진은 같은 렌더에서 사라지고 object URL을 해제. 120초 동안 폴링 실패면 모든 사진 내림.
- 워치독: 프레임 10초 멈춤/오류 → 새로고침(1분에 한 번 이하), 매일 05:00 새로고침.
- 비용: 벽 하나가 분당 12번 피드 + 이미지(처음 한 번씩). 허브에서는 Vercel 호출 0.
- 클라우드에서 벽을 돌리면 노출 기록이 없어 최신순(D52). 공정 로테이션은 허브 벽에서만.

## 6. 성능 (요구사항 4.8)

이번 작업에서 새로 잰 것은 없다. 기존 측정(2026-10-13, `docs/measurements/2026-10-13-phase4.md`):
80분·25분 헤드리스 실행에서 힙·DOM 평평, 재시작·오류 0. **180분 연속 실행, 실제 LED·픽셀 피치·
관람 거리는 미검증**(리허설 H1, D1~D6). 측정 도구는 `measure/`(`playwright.measure.config.ts`)에 있다.
